1. Visión general

Reemplaza dos sistemas de Google Apps Script (visitas/tareas y SOS/SOE) por una aplicación web de costo cero: un sitio estático (HTML + JavaScript puro, sin compilación) y Supabase (PostgreSQL con RLS, Auth, Storage y una Edge Function). Se publica en GitHub Pages.

CapaTecnología
InterfazSPA en JavaScript vanilla, CSS propio, sin framework ni bundler
DatosPostgreSQL (Supabase) con funciones SQL y políticas RLS
AutenticaciónSupabase Auth, usuario + contraseña, código → codigo@cn.app
ArchivosSupabase Storage, bucket privado evidencias
Funciones de servidorEdge Function admin-users (Deno/TypeScript)
Libreríassupabase-js, SheetJS (xlsx), ExcelJS, jsPDF, html2canvas, PptxGenJS (CDN)
HostingGitHub Pages (flujo Actions); alternativa Cloudflare Pages
PruebasPlaywright con Supabase simulado en memoria

2. Arquitectura

Navegador (SPA estática)  ──HTTPS──►  Supabase
  web/*.js                              ├─ Auth (JWT)
  clave pública (anon)                  ├─ PostgREST  ──► tablas con RLS + RPC (funciones SQL)
                                        ├─ Storage    ──► bucket privado «evidencias»
                                        └─ Edge Function admin-users (service role, solo admin)
GitHub (main) ──Actions──► GitHub Pages (publica web/)

No existe servidor propio. Toda la lógica de acceso reside en la base: el navegador usa la clave anon (pública por diseño) y el JWT del usuario; las políticas RLS deciden qué filas ve y modifica cada quien. La clave de servicio nunca llega al navegador.

4. Frontend

4.1 Modelo de módulos

Cada archivo es una IIFE que registra vistas en objetos globales: NAV[clave] = [titulo, roles], VIEWS[clave] = async function, GROUPS (agrupación del menú) y CN.sub[clave] (pestañas laterales). El estado de sesión vive en S (S.me, S.cfg, S.motivos, S.ecmMap, S.roles).

4.2 Enrutado y permisos

La ruta es el hash (#visitas). route() valida con veMod(clave), dibuja el menú y ejecuta la vista. Permisos: veMod (módulo visible), CN.tabOk(mod, pestaña) (pestaña visible) y CN.puede(capacidad) (acción permitida). El administrador pasa todos los controles; el control real está en la base (RLS), la interfaz solo oculta.

4.3 Utilidades comunes

  • esc, norm (sin tildes, mayúsculas), key, g(fila, ...nombres) (lee una columna por alias), TXT, toISO (acepta Date, ISO, dd/mm/aaaa y números de serie de Excel).
  • CN.fetchPar (lectura paginada en paralelo), CN.conReintento (reintentos ante fallos de red), safeUrl (valida enlaces).
  • VZ: kpi, table, hbar, stack, line, msel, tabs y exportadores.

4.4 Convenciones

Accesibilidad (etiquetas, enlace «saltar al contenido», contraste), diseño adaptable a celular, tema claro/oscuro, y todo texto dinámico pasa por esc() para evitar XSS.

5.3 Migraciones

La fuente de verdad es el proyecto Supabase; los schema*.sql son la base inicial y se aplicaron más de 25 migraciones (permisos por región y submenú, tipos de usuario, rendimiento RLS, análisis SOS/SOE, plan, accesos). Para versionarlo completo:

supabase db pull          # crea supabase/migrations/<fecha>_remote_schema.sql
supabase migration new nombre_del_cambio
supabase db push

6. Seguridad y RLS

  • Información pública: el código del sitio (repositorio público), la URL de Supabase y la clave anon. Ningún dato operativo es público: sin sesión, las políticas RLS no devuelven filas.
  • Alcance por rol base (my_role()): admin y gerencia ven todo; supervisor ve su equipo (todos si no tiene nombre asignado) y se limita por regiones; asesor solo su ECM.
  • Permisos por tipo (roles.ver / roles.editar): capacidades carga, ecm, catalogo, metas, justificar, revisar, sos_editar, ganancias. Cargar bases es exclusivo del administrador.
  • Reglas del proyecto: toda política usa (select my_role()) o (select tiene_permiso('…')) (initplan, se evalúa una vez por consulta); nunca políticas ALL de escritura sobre tablas de lectura masiva (regirían también las lecturas), por eso se separan INSERT/UPDATE/DELETE.
  • Funciones: ejecución revocada a public/anon; las SECURITY DEFINER verifican el rol internamente y fijan search_path.
  • Accesos: cada usuario inserta solo sus filas; solo el admin lee y borra.
  • Auth: registro abierto desactivado y confirmación de correo desactivada (los usuarios los crea el administrador). Pendiente: activar protección de contraseñas filtradas (Authentication → Policies).
Si el proveedor Email de Supabase se desactiva, el login falla con 422 email_provider_disabled. Mantener: Email habilitado, «Allow new users to sign up» y «Confirm email» apagados.

7. Autenticación y usuarios

  • El código ingresado se convierte en codigo@cn.app y se autentica con signInWithPassword. No se envían correos.
  • boot() lee profiles, roles, config, motivos y ecm_map; si el perfil está inactivo, cierra la sesión.
  • Edge Function admin-users: alta, cambio de clave y baja de usuarios con la clave de servicio, solo si quien llama es administrador. Despliegue: supabase functions deploy admin-users.
  • Cada usuario nuevo requiere su fila en profiles (la función la crea junto con el usuario de Auth).

8. Almacenamiento de fotos

Bucket privado evidencias: solo JPG/PNG/WebP de hasta 2 MB; las políticas de Storage limitan escritura y lectura según el rol y el ECM dueño del registro; la interfaz abre las fotos con URL firmadas temporales. Las URL de fotos de Involves (Azure) se guardan como texto y se validan con safeUrl.

9. Pipeline de carga de bases

  1. Lectura (leerArchivo): CSV (detecta codificación UTF-8/Windows-1252 y delimitador; se lee sin conversión automática de fechas para respetar día/mes) o Excel con SheetJS (cellDates). Los .xlsx de más de 12 MB (no tareas) usan xlsx_stream.js, un lector en flujo que descomprime y procesa por bloques con barra de progreso.
  2. Detección (detectar): encabezados normalizados (sin tildes, mayúsculas, sin espacios) → tipo: VISITDATE=visitas, ESTADOTAREA=tareas, CLIENTESAP+NOMBRECLIENTE3=rutero, ECM+TELEFONO=equipo, DESCRIPCIONPREGUNTA+RESPUESTA+CODIGOCLIENTE=encuestas, PERFILDELPDV+EMPLEADO=espacios/enlaces.
  3. Mapeo (mapVis, mapTar): normaliza fechas con toISO (incluye números de serie de Excel, p. ej. 46327 = 2026-11-01), construye el id determinista y clasifica. Filas sin fecha, cliente o ECM se descartan y se cuentan como omitidas.
  4. Escritura (cargarVT): modos actualizar (upsert por id, compara columnas para contar nuevas/actualizadas/sin cambios), rango (borra por día y recarga) y todo. Lotes con reintentos.
  5. Resultado: resumen de la carga, registro en cargas y panel de error persistente (ERRCARGA) si algo falla.

Identificadores idénticos a los del sistema original: V|fecha|cliente|BDR y T|fecha|cliente|hash (hash djb2 en base 36 de la descripción); los duplicados reciben sufijo #n.

10. Reglas de negocio

ReglaDetalle
Categoría de tareaVALID+FINISHED → E; INVALID+FINISHED → M; JUSTIFIED → F; AVAILABLE → P; FINISHED → M; otro → P
Tarea de fríoExpresión COOLER|ESPACIO FRIO|NEVERA sobre pilar + descripción normalizados (configurable; se recalcula con «Recalcular»)
Semana operativaconfig.semana_inicio (3 = miércoles); inicio de semana = fecha − ((dow − inicio + 7) mod 7)
Encuestas SOS/SOESe excluyen lunes y martes (día operativo > 4); una visita por PDV, tipo de encuesta y semana (la más reciente); PDV de excluir_pdv fuera; solo valores > 0
Puntaje20 % visitas, 30 % tareas, 30 % tareas de frío, 10 % SOS, 10 % SOE (pesos en config), contra metas por defecto o personalizadas (metas)
MotivosResponsable CN no penaliza; otro responsable penaliza

11. Rendimiento

  • Agregaciones en SQL (share_agg con CTE MATERIALIZED) en lugar de traer filas al navegador; se corrigió un caso de 39 s.
  • Políticas con initplan y políticas de escritura separadas de las de lectura.
  • Índices por fecha y por usuario (también en accesos).
  • Lecturas paginadas y paralelas (fetchPar) con reintento; renderizado de tablas por páginas.
  • Lector en flujo para .xlsx grandes (evita agotar memoria del navegador).

12. Pruebas

npm install
npx playwright install chromium
npm run check        # sintaxis de web/*.js
npm test             # dup.js (filtros duplicados) + run.js (todas las pantallas por rol) + reg.js
npm run test:todo    # además vt2.js (exportaciones) y pl.js (plan/alcance)
node tests/subir-real.js ruta/archivo.xlsx   # sube un archivo real contra el Supabase simulado

Las pruebas usan tests/fake.js, una simulación en memoria del cliente Supabase (tablas, filtros, RPC), por lo que nunca tocan datos reales. Resultados y capturas en tests/out/. Auditorías extra: aud.js (accesibilidad), lay.js (maquetación), sv.js y xlsx-grande.js.

15. Resolución de problemas

SíntomaCausa probable y solución
Nadie puede ingresar (422 email_provider_disabled)Reactivar Email en Authentication → Sign In / Providers
Usuario sin acceso a nadaFalta fila en profiles o activo = false
Carga de tareas: «no hay filas válidas»Fechas como número de serie de Excel (corregido en toISO); verificar columnas SystemModstamp, CodigoCliente, SectorDesarrollo
Fechas con día y mes cambiadosCSV leído con cellDates (SheetJS usa mes/día); corregido leyendo CSV como texto. Para datos ya cargados, intercambiar día y mes por SQL
Consultas con «statement timeout»Revisar plan de la función (usar CTE MATERIALIZED, evitar auth.uid() sin select)
Pages no se actualizaRevisar Actions; si hay «Found 0 artifact(s)», volver a ejecutar el flujo; eliminar flujos duplicados (jekyll/static)
Cambios no visiblesCtrl+F5 (caché del navegador)
Archivo grande se cuelgaSe procesa con el lector en flujo (> 12 MB); si falla, dividir el archivo por fechas
